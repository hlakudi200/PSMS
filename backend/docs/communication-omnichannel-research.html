PSMS · Research Brief

What it actually takes to say PSMS
“communicates across all channels”

A definition, a maturity model, where PSMS sits today, and the platform you’d build to get there.

The short answer. “All channels” is not a feature you bolt on — it’s a platform capability. Anyone can call a Twilio API. What lets you claim omnichannel is the layer underneath: one place that decides who to reach, on which channel, in what order, respecting their consent, and that knows whether it actually arrived.

PSMS today is single-channel (in-app only). The database has EmailSent/PushSent columns, but nothing is wired — no email, SMS, push, or WhatsApp, no queue, no preferences, no delivery tracking. So the honest status today is in-app only, not multi-channel.

1 · Multi-channel ≠ omnichannel

Multi-channel (the easy half)

You can send on several channels, but each is its own silo with its own code, its own “to” field, no shared preferences, no idea if the others fired. Sending the same notice 4 times, 4 ways.

Omnichannel (the bar)

One event → one decision → the right channel(s) for that person, in priority order, deduplicated, consent-checked, tracked end-to-end, with automatic fallback when a channel fails. Channels are interchangeable plugins behind one service.

So the research question reframes: not “which channels do we add?” but “what platform makes channels interchangeable, governed, and observable?” The channels are the cheap part. The 11 capabilities in §3 are the expensive, defensible part — and they’re what “scalable” really means here.

2 · The channels (and what they’re for)

Each channel has a job. For a South African school, the order of value is roughly WhatsApp → SMS → in-app/push → email → voice. WhatsApp open rates sit around 98% and it carries PDFs/images cheaply — it’s the primary parent channel in SA, not a nice-to-have.

3 · The 11 capabilities that actually define “omnichannel”

This is the real checklist. Channels plug into these; without them you have silos, not a platform.

01 · ABSTRACTION

Channel-agnostic dispatch service

One INotificationDispatcher with a provider interface per channel. App code says “notify user X about event Y” — never “call Twilio”. Adding RCS later = one new adapter, zero call-site changes.

02 · ASYNC

Queue + workers (decoupled send)

Sending must not block the request. A message queue buffers, background workers dispatch, so a 5 000-parent announcement doesn’t time out the API. ABP Background Jobs / Hangfire / a broker.

03 · IDENTITY

Contact & device resolution

Per recipient: verified email, MSISDN, WhatsApp number, push device tokens — and the logic to resolve “what addresses does this person have?”. Today PSMS has no phone/token fields.

04 · CONSENT

Preferences & opt-in/out (POPIA)

Per-user, per-channel, per-category preferences + quiet hours + STOP handling. POPIA §69 requires opt-in for anything marketing-like and a working opt-out. This is legal, not optional.

05 · TEMPLATING

Per-channel, localized templates

One logical message → SMS (160-char), WhatsApp (pre-approved template), email (HTML), push (title+body). Variables, and language (SA has 11 official languages — at least EN + local).

06 · ORCHESTRATION

Routing & fallback cascade

The decision layer: “try WhatsApp; if not delivered in N min or no WhatsApp consent → SMS; → email.” Priority, channel cascade, and dedup so one event never spams every channel at once.

07 · DELIVERY

Status tracking & provider webhooks

queued → sent → delivered → read → failed, fed by provider callbacks. Without this you can’t do fallback, can’t prove a parent was notified, can’t debug. Today: two boolean stubs.

08 · RESILIENCE

Retries, dead-letter, idempotency

Transient failures retry with backoff; permanent ones dead-letter for inspection; an idempotency key stops a retry from double-sending. Rate-limiting/throttling to respect provider caps.

09 · REAL-TIME

Live in-app transport

SignalR (already in the project, not wired) pushes the bell badge + notification centre instantly instead of polling. The in-app channel’s “delivered” event.

10 · INBOUND

Two-way messaging

Replies and inbound WhatsApp/SMS routed back to a conversation, plus keyword handling (STOP/HELP). Turns broadcasts into conversations — and is how opt-out legally works.

11 · GOVERNANCE

Audit, analytics & observability

Who was sent what, when, on which channel, and did it land — for compliance and for tuning (open/delivery rates per channel). Structured logs: event, user, channel, status, latency.

Cross-cutting: scheduling & event triggers (send at a time / on a domain event), batching for bulk sends, and cost controls (channel choice has real per-message cost in SA).

4 · Maturity model — where PSMS sits

Level 0
Single-channel — in-app only; messages/notifications live in the DB and are read in the app. PSMS is here
Announcements have publish/expiry; SignalR present but unused; email/push columns are stubs.
Level 1
Multi-channel (siloed) — email + SMS + push wired, but each ad-hoc, no shared preferences, no delivery feedback.
Level 2
Preference-aware — one dispatch service, per-user channel preferences + consent, templates, delivery status, async queue.
Level 3
Orchestrated / omnichannel — routing + fallback cascade, inbound/two-way, real-time, analytics. Now you can honestly say “all channels”.

6 · Target architecture for PSMS

The shape that satisfies the checklist without rebuilding later. App code raises a notification request; everything else is the platform’s job.

Build (yours)

The dispatcher, preferences, contact/template stores, queue wiring, delivery log, the provider interface, and the in-app/SignalR adapter. This is the durable IP.

Buy / integrate (providers)

WhatsApp (Meta Cloud API or CM.com/Clickatell), SMS (Clickatell/Twilio), email (SendGrid/SES), push (FCM/APNS). Swappable behind the interface. Or a single CPaaS (Infobip/Twilio/CM.com) to cover several at once.

7 · A pragmatic roadmap

  1. Foundations (no new channel yet). Notification dispatcher + provider interface, async queue (ABP background jobs), contact/device fields on users, a delivery-status lifecycle, and the in-app notification centre + SignalR. Turns Level 0 into a real platform with one channel.
  2. Preferences & consent. Per-user channel/category preferences, POPIA opt-in/out, quiet hours — before sending on any external channel, because it’s a legal gate.
  3. First external channel: WhatsApp. Highest SA value (98% open, PDFs). Adapter + pre-approved templates + inbound webhook for STOP/replies + delivery webhooks.
  4. SMS fallback + Email. SMS as the universal fallback when WhatsApp isn’t consented/delivered; email for formal/long-form + attachments. Now the fallback cascade is real.
  5. Push + orchestration + analytics. Mobile/web push, the routing/fallback rules, and per-channel delivery dashboards. This is when “all channels” becomes an honest claim (Level 3).

POPIA is a hard gate, not a footnote

Under South Africa’s POPIA, contacting parents on external channels needs a lawful basis and a working opt-out; anything marketing-flavoured needs explicit opt-in (§69). WhatsApp Business API requires recipient permission before you message them. So preferences + consent (capability 04) must land before the first external send — it’s sequenced into step 2 deliberately.

Bottom line

To claim PSMS “communicates via all channels,” you don’t need every channel on day one — you need the platform: a channel-agnostic dispatcher, async delivery, consent/preferences, templates, delivery tracking, and fallback. Add channels as adapters into that. Today PSMS is Level 0; the roadmap above reaches Level 3 in five sequenced moves, with WhatsApp as the highest-value first channel for the SA context.
